## What was merged

- Core (`bridge_core.[ch]`): 0xd0 status, 0xd1/0xd2 MCU passthrough + events, 0xd3 GPIO test, 0xd4 log forwarding, 0xd8..0xdc update dispatch.
  All of today's code is kept: WiFi AP/STA/scan (0xc6..0xc8), ARP proxy, wake on TCP SYN, T30 auto reset, `XR_PIR`, `S.usb`.
- `fw_update.[ch]`: unchanged from the features copy.
- `bridge_core.h` was rebuilt by hand from the current header. The new hooks are appended **after `wifi_mode`**, not after `set_ready_pin` as in the old base, so main.c's positional initialiser still fits.
- `MCU_Q_STATE1` keeps today's fix (`S.usb` from the boot `{0x1e}` answer) and also fills `mcu_usb`, `mcu_state1` and the seen bits. Status therefore shows USB from boot on.
- xr871d: the three rejected hunks (includes/version, `ctl_input`, usage/getopt) were applied by hand; the `-c` client waits for the daemon's answer.

## What was dropped or changed, and why

| Item | Decision | Reason |
|---|---|---|
| `spi_slave.c` hunks | Dropped except the `spis_ready_pin()` getter | The patch silently reverted two current fixes: `allowed_pins = { 15 }` back to six pins, and the reset-loop timeouts in `fifo_reset`/`ctrl_init`. |
| `wifi.c` RSSI hunk | Dropped, rewritten | Fuzz 3 placed it inside `sec_type()` (scan security), where it did not belong. Now `wifi_link_info()` (the existing 10 s diagnostics) caches `level` in dBm and `wifi_status()` returns the cache. No new WLAN call under the core lock. |
| `hal_ext.c` AXP2601 read | Dropped | One implementation: main.c `bat_read`/`bat_report` (hardware proven, stock model). `bat_report` hands each reading to `hal_ext_battery_set()`; status reports that copy (unknown if older than 120 s). Status never touches the PMIC. |
| `hal_ext.c` log function | Dropped | One implementation: main.c `h_log()` now formats into a static buffer (own mutex) and calls `bridge_log_capture()`. No extra stack on the SPI thread or the SDK WLAN receive path. |
| `hal_ext.c` flash init flag | Unified | `hal_ext_flash_init()` is the only `HAL_Flash_Init` state; main.c `flash_init_once()` calls it. The old code assumed "platform_init already did it", which is wrong before the service window ends. |
| Flash hooks | Hardened | Erase and write below 0x8000 are refused in the glue as well as by the `fw_update.c` window check. Sector 0 is never written at runtime. |
| GPIO test | PA10 refused in the glue | PA10 is the charge LED that `led_update()` rewrites every second. PA15 (ready pin in use) was already refused. |
| `gpio scan` default list | Removed | PA6/11/13 have unknown roles (today's comment in `spi_slave.c`: T30 power/reset?). `gpio scan` without pins now prints usage, rc 2; pins must be named. |
| Console `gpio`/`mcu`/`bat` in main.c | Left untouched | Hardware proven. The console keeps its own `diag_pin_ok` list; not unified with `bridge_gpio_protected`. |
| Thread stacks | "mcu" and "t30" 2 KiB -> 4 KiB | README recommendation; the update path goes about 500 bytes deeper. |
| MCU heartbeat events | Not written to the T30 kernel log | 0xd2 is forwarded for every MCU heartbeat; xr871d counts them and logs only other events (all with `-v`). |
| Old `-c` commands | All answer `ok` | `ap`, `sta`, `scan` exist only in today's daemon and now end with `ok`/rc 0 like sleep/stay/wifi/probe. |
| Host model | 0x1e answers 1 (USB), silent on 0x26/0x29/0x2b/0x2c/0x2f | Matches MCU sw 150 as seen today. |

Not done (not part of the features): AXP2601 T2E/T2F (0x0a..0x0d) in the status record; passthrough replies are acked with `{0x0e,val}` like every other MCU message (stock behaviour), 0x1e/0x1f/0x23 answers stay un-acked as in ap17.

## Camera-2 flash and the update path

`xr871-image.py bootsel` on the images:

| Image | Result |
|---|---|
| `flash/xr871-abus-m2-ap17.bin`, ap16, m2, m1 | OTA disabled in the boot header (priv fields 0xff): image 1 only, no fallback |
| `work/xr871m2/xr871-abus-m2-ap18-features.bin` | Same: OTA disabled, boots image 1 |
| `work/xr871.bin` (stock dump) | OTA area 0x100000/0x4000, config 0xaaaa/0x9669, boots image 2 |

- This is the PC image file; the camera itself was not read. The deploy script writes 0x8000..0xc6000 from this file, so the camera should match it apart from sysinfo.
- The ap17 file still carries the stock image 2 chain at 0x104000 and an fdcm record at 0x100000. The bootloader ignores both.
- Consequence: `fwupdate` stages only with `--force-stage` (overwrites the dead stock image 2 copy) and `--commit` is always refused on this flash. The host suite tests exactly this case (section 3).
- The working update path stays `tools/xr871-deploy-app.sh NAME PREV`: service console over the ESP32 monitor, image 1 rewritten in place, no fallback.
- The deploy script keeps working with the new tool: `build` keeps the base image's boot header fields, which are already 0xff.
- Enabling A/B needs `xr871-image.py set-ota` on a full image and a clip flash of sector 0. Not done.

## Open risks

1. Nothing ran on the XR871. First-time code on hardware: 4 KiB stacks, `h_log` with a mutex, log queue, status, GPIO glue, flash hooks called from the t30 thread.
2. UART receive on the XR871 is only active while `t30_task` waits in `HAL_UART_Receive_IT` (64-byte FIFO). A heartbeat frame arriving during a flash erase can lose bytes. xr871d retries chunks (5 tries), other commands time out. Watch `t30 bad` in the status.
3. Flash erase/write and forwarded log lines run under the core lock: the SPI data path stalls for up to about 50 ms per sector during an update and about 18 ms per forwarded line (at most 10 lines/s). Expect network hiccups during `fwupdate`.
4. xr871d enables forwarding on every boot: two XR871 status lines every 10 s go to the T30 syslog (tag `xr871`).
5. `xr871d -c` now blocks until the daemon answers. Scripts (`standby`, `S38xr871portal`, `wlan`, `wpa_cli` shim) wait while the daemon is busy with `probe` or `fwupdate`. A 0.7 client talking to a still-running 0.6 daemon waits 60 s and returns 1.
6. Status battery is the last 30 s reading, "unknown" for the first 10 s after boot. RSSI is 0 until the first 10 s diagnostics run; `level` = dBm is taken from the scan code and not verified against a known signal.
7. `fw_update.c` assumptions from the features README still stand: fdcm format from the SDK source, RAM compare of 1 KiB at APP +0x400, bootloader fallback only on a bad APP checksum.
8. A passthrough reply with command 0x0d/0x12/0x13 is handled like a real PIR/key event.
9. App section headroom is 11.7 KB.

## First hardware test, step by step

Stop at the first step that fails. Only step 9 writes flash outside the normal deploy path.

1. Build Thingino with the package, or copy `work/fwtest/mips-1120/xr871d` to the camera's `/tmp`, stop the 0.6 daemon and start the new one right away. Still on ap17: `xr871d -c status` must answer "no status reply (firmware too old?)"; `sleep`, `wifi`, `probe`, standby and the portal must behave as before.
2. `tools/xr871-deploy-app.sh ap18-features ap17` (rebuilds the same image, writes it over the service console, reboots the XR871). Watch the UART0 log: banner `abus-xr871 fw (wifi) ap18-features`, boot marks up to `init done`, no crash record on the next boot.
3. Regression without using any new command for 10 minutes: network through SPI, `bat:` lines every 30 s, LED, `spis:` diagnostics, one standby cycle with wake by TCP SYN and by PIR.
4. `xr871d -c status`: version string, MCU 150, battery equal to the last `bat:` line, USB state correct, RSSI plausible after 10 s, `t30 bad 0`.
5. `logread | grep xr871`: XR871 lines arrive, no credential text; `xr871d -c status` shows `log dropped 0`.
6. `xr871d -c 'mcu 0x23 0'` (expect `{0x23,0x96}`), `mcu 0x15 0`, `mcu 0x18 0`; `mcu 0x26 0` must report sent and no reply; `mcu 0x05 0x09` must be refused without `force`.
7. `xr871d -c 'gpio PA12 in'`; `gpio PA10 1` and `gpio PA15 1` must be refused. Drive PA6/11/13 only on purpose, one at a time, short hold.
8. `xr871d -c 'fwupdate --info'`: expect running image 1, OTA DISABLED, target window 0x104000-0x1f7000. Read only; first call of the flash hooks.
9. Optional transfer test: `xr871d -c 'fwupdate /tmp/xr871-abus-m2-ap18-features.bin --force-stage'`. It overwrites only the dead image 2 area, takes about 65 s, must end with "verified". Then `fwupdate --commit` must be refused. Afterwards check `t30 bad` and that the network recovered. The image file contains WiFi credentials: remove it from `/tmp` afterwards.
10. Leave it running over one night of standby cycles and compare battery drain with ap17.

Rollback:

- XR871: write `flash/xr871-abus-m2-ap17.bin` back with `tools/xr871-svc-flash.py` (`--old` = the ap18 image, `--from 0x8000 --to 0xc6000 --write`), then `reboot` on the console.
- Do NOT run `xr871-deploy-app.sh ap17 ...` for that: the script copies the current SDK output over `app-ap17.bin` and would rebuild "ap17" from the ap18 code.
- Sources: `work/pre-merge-1120/` holds the pre-merge files; after restoring them run `make clean` in the SDK project.
- xr871d: reinstall the 0.6 binary.

## 2026-11-21 battery features (ap22, host-tested, not on hardware)
- Stock reference: disassembly of the stock app (image 1).
  - Charging timer at 0x13abc (log name `CMU_ChargingTimeOutCallBack`). On USB, when SOC goes from 100 to below 100, it sends `{0x21,0}` then `{0x21,1}`.
  - Heartbeat handler at 0x13e20.. If SOC < 2, no USB and the gauge is valid, it sends `{0x24,val}` ("Low power automatic shutdown").
- Core `bridge_battery()`, called by the glue after every gauge reading (30 s):
  - **Charge restart:** USB present and SOC drops from 100 to below 100 -> `{0x21,0}`, `{0x21,1}`. Counted.
  - **Low-battery shutdown:** sends `{0x24,0}` once. Conditions:
    - USB known to be absent (never while unknown);
    - SOC < 2 % in 3 readings in a row;
    - VBAT < 3600 mV (protects against a gauge reading 0 %).
    - It is re-armed when USB power returns.
  - **T2E/T2F:** AXP2601 0x0a..0x0d are read (4 bytes) and appended to the battery frame 0xcc (u16 t2e, u16 t2f). They are also in the status tail.
- Status reply 0xd0 grew from 152 to 160 bytes:
  - 152 t2e; 154 t2f; 156 charge restarts; 158 low-battery count (0xff = shutdown sent).
  - The version string stays at 88..151, so old xr871d builds still parse it.
- xr871d:
  - `status` shows "time to empty" only on battery below 100 %, plus the charge restart and low-battery lines.
  - `/run/xr871d.battery` gets `t2e_min=` under the same condition.
- Inferred, not verified: the meaning of `{0x21,0}` (charging off?) and of the `{0x24}` value. A hardware test with USB plugged in is pending.
- Tests: `tests/battery.c` (20 checks); run_tests.py 126/126; PARSER PASS; HOST SLEEP PASS. SDK build 141004 B; image 7/7 sections ok.

- 2026-11-21 09:30 ap22 on camera 2: T2E shown (7 h 17 min at 45 %, T30 on), no unintended {0x21}/{0x24}. Charge restart and shutdown not yet triggered on hardware.
